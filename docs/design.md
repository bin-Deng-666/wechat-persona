# 对话设计

目标是连续、自然、能够纠正和停止的微信单聊。人格负责表达习惯；对话协调器负责输入、当前活动和交付的真实顺序。通道不定时主动搭话。

## 运行结构

```text
微信/iLink → 持久化原始消息 → 每个联系人的对话协调器 → DSH agent
                                   ↑                    ↓
                           补充 / 停止 / 新对话     durable 会话事件
                                   ↓                    ↓
                            任务与个人记忆       有序文字/表情/文件队列
                                                        ↓
                                                  逐项交付状态
```

- `wechat/channel.ts` 管理轮询、控制入口、原文/附件组装与事件路由。
- `chat/conversation.ts` 管理一个联系人的活动、输入准备顺序和可撤销的输出版本。
- `chat/history.ts` 持久化原始消息、提交批次、交付结果、控制反馈和任务快照。
- `dsh/` 使用宿主的会话、steering、工具注册、审批、附件与压缩服务。
- `memory/` 管理有原话证据的个人信息，和当前任务状态分别存储。
- `reply/queue.ts` 串行发送文字、表情和文件，给出逐项结果。

## 输入与轮次

同一联系人的接收与设置变更按顺序执行，先把原始消息写入私有文件，再允许轮询游标前进。消息 ID 按联系人隔离，重启后仍可去重。没有 ID 的消息分配本地身份，不能宣称具备跨进程去重。

连续消息采用 650ms 静默窗口，最长聚合 1800ms；窗口只决定输入批次。处理中的补充使用 DSH `steer()` 在下一步骤消费，空闲时用 `followup()` 开始新轮次。补充到达后撤销尚未发出的旧版本输出；新补充未进入模型前，旧模型结果不能被当成对它的回答。

媒体下载按联系人提交顺序处理，不阻塞其他联系人。取消信号传入下载和发送。原始消息内的文字/图片顺序、引用 ID 和收到时间保留；系统提供来源索引，用户正文不添加人格或控制提醒。

批次有稳定的 DSH message ID。含特殊字符的联系人 ID 使用独立的哈希命名空间，防止简单替换标点造成会话碰撞；旧版对应的宿主日志保留，升级后不自动改写或合并它们。恢复未完成提交时检查宿主的 durable inbox 和会话历史，避免因插件在提交前后退出而重复投递。关闭插件时保留尚未提交的输入供重启恢复；用户明确停止时取消相应待办。

## 一个活动的生命周期

活动关联当前代次、原始输入、取消信号、宿主轮次与输出版本。`turn/start` / `user/message` / `turn/end` 用于确认消息消费和完成，旧轮次事件不能结束新的活动。

- **停止**：立即使当前活动失效，撤销待发送内容，取消模型/维护任务和审批，给一次控制反馈。已经被服务端接受的消息保持原交付结果。
- **新对话**：先停止旧活动，再持久化新代次。旧代次的回答、文件和结束事件不再进入当前微信对话，旧历史保留。
- **压缩**：在空闲阶段使用宿主 `compactNow()`；工作在接收循环之外执行。停止或新输入可取消维护任务，迟到的压缩反馈不能进入新活动。
- **设置**：设置先提交，后续输入才能使用新值。菜单发送和模型推理不占住全局轮询。

## 用户能看到的交付

回复按正文中的原顺序解析为文字、表情、文件单元，保留显式 `[分条]` 边界。文件与说明文字进入同一队列。每个单元拥有固定发送 ID，重试时复用；不假定协议保证 exactly-once。

```text
pending → sending → accepted / failed / unknown
    └─────────────→ cancelled
```

`accepted` 仅表示微信服务端接受，不是用户已读。网络请求已开始而响应不明时记录 `unknown`，不能写成成功。回答部分成功时返回 `partial`，后续上下文能看到实际状态。

组内与后续排队内容在发送前持久化。进程在发送期间退出后，`sending` 恢复为 `unknown`；尚未发送的旧回答取消，避免重启突然补发过期内容。用户可依据交付状态要求重试。重试和重启都不保证收件端绝无重复。

不额外模拟随机思考停顿；模型和网络的实际等待已计入用户体验。相邻单元保留发送节流与有限退避。系统提示、审批和错误同样走队列，不绕过顺序或取消机制。

## 系统提示词与自然表达

`PeerSystemPrompt` 仅安装到当前微信 agent，并检查精确 agent 身份。子 agent 不继承联系人设定。每次请求读取当前人格、沟通偏好、表情目录和对话状态；保留宿主工具规则，渲染后使用 `interpolate: false`。

基础对话规则要求采用最新更正，信息足够就继续，必要时只问关键缺失项。情绪表达可以先得到回应；确认、道别和自然结束不强行追加问题。不虚构执行结果、私人经历或关系。

人格卡的字数是闲聊风格目标，任务回答按需要完整表达。聊天里的“分条 N”只调整发送形态，不把整个回答限制为 N 字。时间包含日期、时区下的星期与时刻；引用只有 ID 且无法解析时不猜测正文。

## 个人记忆与任务状态

个人记忆部分迁移自 MIT 项目 `agent-personal-memory`：分类与确定性、来源模型、去重和搜索、证据检查、版本冲突及删除抑制。没有迁入 pi UI、全局用户记忆文件或历史扫描后台任务。许可见 [../NOTICE.md](../NOTICE.md)。

- `wechat_memory_search`：只检索当前联系人，返回 ID、版本、范围与来源，用于相关话题回忆和写入前去重。
- `wechat_memory_write`：只接受当前活动的真实用户消息 ID 与逐字引用。更新必须先检索确切版本并有明确更正；删除必须引用当前明确请求。每个活动最多三次写入。
- 普通对话只自动注入沟通协作习惯，其他类别按相关话题检索。记忆是数据，不能升级为系统指令。
- 自动检查能拦截明显的错误来源、项目细节和过度推断，不能证明所有概括语义都正确；模型仍须遵守个人价值与证据规则。
- 删除后保留内容/来源抑制键，避免自动重新收录同一信息。
- `wechat_task_update`：保存当前任务的目标、最新约束、完成、待办和等待事项。快照与个人记忆独立，压缩后仍可见，新代次不继承旧任务。

工具注册在会话作用域，执行时再次检查确切 agent 和取消信号。其他联系人、GUI 会话、子 agent 不能利用继承的工具访问这份记忆。

旧版 `memories.json` 中没有原话来源的字符串作为“旧版未核实”资料保留并可在菜单查看。原文件保留，不编造证据，也不自动注入。损坏文件报错并保留，不用空库覆盖。

## 验证边界

自动测试覆盖实际 DSH 提示词/工具组装、原始输入顺序、steering、取消、代次隔离、交付结果与重启恢复，以及记忆的来源、版本、删除和隔离。固定多轮语料的人工/真实模型验收见 [evaluation.md](evaluation.md)。通过接线测试不等于对话质量已经达标。

微信真机仍需检查 iLink 回执行为、引用解析范围、图片/GIF 客户端显示和真实网络下的重试。发送结果不明时不宣称已送达或未送达。
